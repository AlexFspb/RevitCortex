# Команды сторонних плагинов через Cortex

Реализация Issue #3. Сборка `2026.10.30-addin-review.14`, контракт API 1.
Ветка `feat/registered-addin-commands` основана на `fix/per-instance-revit-port`.
Изменение не устанавливает адаптер MEP и не меняет расчётные формулы.

## Что реализовано

Плагин регистрирует именованные команды через `AddinRegistry.Shared.Register(provider)`.
Агент видит схемы, режимы, версию загруженного модуля и его MVID.
Агент вызывает настоящий обработчик установленного плагина через MCP.
Обработчик работает синхронно в штатном ExternalEvent Cortex, без выбора элементов и окон.

Принимается только одна операция. Следующий запуск получает `Busy`.
Если общий слот занят обычным инструментом и событие не принято, Cortex возвращает `Busy` без записи UUID.
После освобождения слота можно повторить тот же запрос с тем же UUID. Такие отказы не расходуют лимит истории.
Это правило относится только к достоверному отказу до приёма события.
Исключение планировщика сохраняется как failed; принятые или неопределённые операции нельзя удалять ради повторного запуска.
Состояние `queued` означает ожидание единственного события Revit, а не очередь следующих заданий.
Обычные инструменты Cortex используют тот же обработчик и тот же занятый слот.
Проверка статуса и отмена используют отдельные TCP-соединения и не ждут освобождения UI или MCP-мьютекса.
Сетевое ожидание не прерывает выполняющийся код Revit.

Существующие порты, автовыполнение, ручное подтверждение при выключенном автовыполнении и индикация сохранены.
Запросы новых инструментов вызывают обычную индикацию активности Cortex.

## Пять MCP-инструментов

| Инструмент | Назначение |
|---|---|
| `addin_list` | Реестр команд, схемы, режимы, MVID, поколение плагина и снимок контекста Revit |
| `addin_execute` | Проверка запроса и приём одной операции; немедленный ответ с `operationId` |
| `addin_get_operation` | Состояние, диагностика и страницы результата по `operationId` или `requestId` |
| `addin_cancel_operation` | Отмена ожидания или запрос согласованной отмены выполняющегося обработчика |
| `addin_reload` | Перезагрузка через зарегистрированный стабильный загрузчик; произвольный путь DLL не принимается |

`addin_list.context` содержит `instanceId`, PID, фактический порт, `documentToken`, `documentGeneration`, название и путь документа.
`documentToken` обозначает текущий контекст документа. После переключения/повторной инициализации он меняется.
Это не постоянный идентификатор файла. При пустом Revit значение равно `null`.
`pluginGeneration` берётся из записи выбранного поставщика.

Передайте эти значения в `expectedContextJson`. Не вычисляйте их самостоятельно.
Для команд с `requiresDocument=true` Cortex проверяет токен и поколение при приёме, в событии Revit и после подтверждения.
Нативная проверка дополнительно сравнивает активный Document с документом сессии и запрещает открытую транзакцию.
Команда без требования документа проверяет экземпляр и поколение плагина; общий обработчик также отвергает смену контекста во время ожидания события.
Для такой команды отсутствие документа допустимо. Служебный RVT автоматически не создаётся.

Новые инструменты имеют собственный явный контракт контекста.
Они не меняют привязку обычных инструментов MCP. Для обычной работы продолжайте использовать `get_project_info`/`say_hello`.
Статус/отмена требуют `instanceId`, но доступны после смены активного документа.
Соединение остаётся на заданном порту. Автоматического перехода к другому Revit нет.

Пример аргументов MCP после `addin_list`:

```json
{
  "requestId": "2a2a2899-0d05-4eb9-b287-57a707f4d35f",
  "pluginId": "cortex-test",
  "operationName": "test.set_project_number",
  "expectedContextJson": "{\"instanceId\":\"ИЗ_ОТВЕТА\",\"documentToken\":\"ИЗ_ОТВЕТА\",\"documentGeneration\":1,\"pluginGeneration\":1}",
  "argumentsJson": "{\"expectedTestDocumentTitle\":\"CORTEX_TEST_Addins\",\"value\":\"TEST-42\"}",
  "mode": "probeRollback",
  "queueTimeoutSeconds": 30
}
```

UUID в примере нельзя повторно использовать для новой операции.
`argumentsJson` и `expectedContextJson` — строки JSON в MCP. В TCP-протоколе это объекты `arguments` и `expectedContext`.

## Результат и повторные запросы

Состояния: `queued`, `running`, `cancelRequested`, `succeeded`, `failed`, `cancelled`, `rolledBack`, `expired`.
Терминальный результат публикуется после выхода из обработчика и освобождения его блокировки.
Исключение при очистке даёт `ProviderCleanupFailed`, даже если транзакция уже зафиксирована.
`queued` может истечь через 1–120 секунд, по умолчанию 30. Истёкшая команда не исполняется позднее.
Занятый слот освобождается только после фактического завершения события, включая отменённое ожидание.

`cancelRequested` не означает откат. Выполняющийся поставщик должен сам проверять токен отмены и возвращать проверенный итог.
Принудительного прерывания потока, закрытия чужих окон и отмены команды пользователя нет.
Поставщик без `supportsCancellation` отклоняет отмену после начала своего обработчика.
До вызова обработчика отмена допустима; ожидающее подтверждение Cortex получает штатный запрос завершения.
Отмена после фиксации не переписывает успешный результат и не отменяет изменения задним числом.

Повтор того же UUID с тем же каноническим запросом возвращает прежнюю операцию.
Другие аргументы, режим, контекст или срок ожидания с прежним UUID дают `RequestIdConflict`.
Перед вычислением хеша Cortex подставляет `queueTimeoutSeconds=30`, если значение пропущено.
Пропущенное значение и явное `30` обозначают один запрос.
Регистр шестнадцатеричных букв UUID не влияет на приём, поиск или отмену по requestId/operationId.
После потери ответа сначала запросите статус по `requestId` либо повторите **тот же** запрос.
Не создавайте новый UUID для слепого повтора изменения.

Записи о принятых UUID сохраняются в памяти до завершения процесса, максимум 10 000.
После достижения лимита новые операции отклоняются. Старые UUID не начинают исполняться заново.
Полные результаты/диагностика сохраняются для последних 128 завершённых операций, суммарно до 32 МиБ JSON.
После вытеснения ответ содержит `resultExpired=true`; ID, итог и защита от повтора остаются.
Аргументы после завершения освобождаются. В записи остаётся хеш запроса.
После перезапуска `instanceId` меняется. `InstanceChanged`/`UnknownOutcome` не доказывают отсутствие прежних изменений.
Журнал служит диагностикой, а не автоматическим восстановлением или повторным исполнением.

Размер запроса и диагностики ограничен 1 МиБ, результата — 8 МиБ. Глубина JSON — 32.
`resultPage.text` содержит часть JSON-текста. Соедините страницы, затем разберите JSON один раз.
`nextOffset` задаёт следующий индекс UTF-16; не вычисляйте его по числу байтов.
Страница содержит до `resultCount` единиц UTF-16, максимум 65 536, плюс одну единицу для целой суррогатной пары.
`totalLength` показывает полный размер в единицах UTF-16. Усечение результата не маскируется под полный ответ.

Ответ сохраняет `transactionOutcome`, `modelChanged`, `externalEffects`, версию и MVID исполнителя.
Ошибка формата ответа **не отменяет** уже зафиксированную транзакцию поставщика.
Поэтому поставщик должен сформировать и проверить ответ до окончательной фиксации группы.
При исключении без достоверного итога Cortex сообщает неизвестные эффекты, а не выдуманный откат.
До завершающей проверки Revit Cortex сохраняет поля ответа и ограниченную диагностику в `providerReceipt`.
Если проверка не проходит, операция имеет state=failed, `postExecutionCheckPassed=false` и неизвестный общий итог транзакций.
Сведения о прежнем commit/rollback остаются в providerReceipt как утверждения поставщика.
`postExecutionCheckPassed=true` подтверждает только проверку контекста API и отсутствия открытой транзакции, а не независимую проверку модели.
Подробный результат поставщика после такой ошибки не подменяет проверку фактического состояния.

## Контракт поставщика

Типы находятся в `RevitCortex.Core.Addins`; Core не ссылается на Autodesk API и не зависит от MEP.Core.

```csharp
IDisposable registration = AddinRegistry.Shared.Register(new MyProvider());
// Перед выгрузкой, после завершения операций:
registration.Dispose();
```

`IAddinCommandProvider` содержит `Describe`, `TryEnter(out IDisposable lease)` и `Execute(AddinExecutionContext)`.
`Describe` вызывается при регистрации/перезагрузке. Каталог читает только сохранённые примитивные метаданные.
`ModuleId` должен быть `ModuleVersionId` реально загруженного расчётного модуля, а не файла на диске или стабильного загрузчика.
MVID автоматически меняется при изменении сборки. Это идентификатор модуля, а не криптографический хеш файла.
Каталог также возвращает `buildId="mvid:…"` и `loadedModuleSha256`, если поставщик сохранил хеш загруженного образа.
Загрузчик MEP должен вычислять SHA-256 тех же байтов, которые передаёт в LoadFromStream, и сохранять его для Describe.
Демонстрация вычисляет SHA-256 при создании поставщика и проверяет MVID файла перед публикацией хеша.
`LoadedVersion` также берётся из загруженной сборки. `pluginGeneration` ведёт Cortex.

`TryEnter` выполняется на UI-потоке и должен немедленно получить общую блокировку программного пути и UI плагина.
При занятости он возвращает `false`. Cortex выдаёт `ProviderBusy` без вызова `Execute`.
При ручном подтверждении блокировка остаётся занятой до ответа пользователя и окончания операции.
Это намеренно запрещает параллельный запуск через окно плагина во время согласования.
Отказ или ошибка подтверждения освобождают блокировку в finally.
Состояние каталога `ready` означает регистрацию и отсутствие операции Cortex; оно не доказывает, что окно плагина свободно.
Снятие регистрации доступно только через IDisposable, полученный из Register; публичного Unregister по ID нет.
Во время операции нельзя снимать регистрацию. Старый регистрационный дескриптор не снимает новую регистрацию с тем же ID.

`Execute` получает `UIApplication` как `object`, JSON аргументов, режим, токен отмены и `ReportStage`.
Приведите тип только внутри синхронного вызова. Не сохраняйте API-объекты для фонового потока.
Не вызывайте второй ExternalEvent с ожиданием на том же потоке. Не открывайте обязательные окна и диалоги сохранения.
Верните `AddinCommandResult` с JSON-данными и явным результатом транзакции.
Согласованную отмену возвращайте через `Status="cancelled"` с явным итогом транзакций и признаками эффектов.
После отката укажите rolledBack; при отмене до изменений без транзакции укажите none.
Не используйте OperationCanceledException как подтверждение отката: без ответа Cortex оставит failed и неизвестные эффекты.
Диагностика — JSON-массив; сохраняйте код, текст, severity, FailureDefinitionId и числовые ID элементов.
Исключение поставщика отражается отдельным `error` в состоянии операции.

Поставщик — доверенный установленный код. Контракт не является песочницей для произвольной DLL.
Установленный плагин обязан честно объявлять изменения и соблюдать режимы. Cortex проверяет декларации и итоговые признаки.
Он не может механически перехватить каждое внутреннее обращение сторонней DLL к Revit или файловой системе.
Произвольные методы, пути DLL, PostCommand и экранная автоматизация не предоставляются.

### Схемы API 1

Поддержаны `type`, `properties`, `required`, `additionalProperties=false`, `items`, `enum`,
`minimum`, `maximum`, `minLength`, `maxLength`, `minItems`, `maxItems`, `title`, `description`.
Тип задаётся явно: object, array, string, integer, number, boolean, null.
Аргументы имеют корневой тип object. Массив требует схему items. Вложенность схемы ограничена 16.
Неизвестные ключи схемы отклоняются при регистрации, а не молча игнорируются.
Это ограниченный профиль JSON Schema; `$ref`, `oneOf`, шаблоны регулярных выражений и произвольные расширения пока не поддержаны.

### Транзакции и безопасность

API 1 поддерживает только `transactionOwner="provider"`. Cortex не открывает внешнюю транзакцию.
`preview` не имеет изменений документа или внешних данных.
`probeRollback` выполняет ограниченную реальную пробу и проверяет полный откат TransactionGroup.
`commit` применяет результат. Успех записи требует `TransactionOutcome="committed"`.
Успешная проба возвращает `Status="rolledBack"`, `TransactionOutcome="rolledBack"` и оба признака эффектов `false`.
Ошибка или отмена после проверенного отката могут вернуть Status=failed/cancelled с TransactionOutcome=rolledBack и обоими эффектами false.
Cortex сохраняет исходные статус, результат и диагностику; EffectsMismatch в этом случае не возникает.
Ошибка или отмена до изменений без транзакции могут вернуть TransactionOutcome=none с обоими эффектами false.
Значения committed/unknown и оставшиеся эффекты по-прежнему не принимаются как безопасная проба.
Внешние записи запрещены в `probeRollback`; такая комбинация метаданных отклоняется.

До изменений каждой транзакции настройте IFailuresPreprocessor и SetClearAfterRollback(true).
Сохраняйте примитивную диагностику. Неожиданные предупреждения/ошибки должны откатывать тестовую операцию.
Проверяйте Commit, RollBack, Assimilate и состояние затронутых данных после пробы.
Не выдавайте временные ID после отката как существующие элементы.
Нативное падение Revit и все возможные модальные окна контракт перехватить не может.

Глобальный режим чтения блокирует команды с `mutatesDocument` или `externalEffects` во всех режимах, включая preview/probeRollback.
Это намеренно консервативно. Для чтения зарегистрируйте отдельную команду без этих признаков.
Изменение разрешений повторно проверяется перед фактическим вызовом.
Изменяющие команды используют существующее подтверждение Cortex. Адаптер не меняет политику автовыполнения.
Отключение MCP-инструмента в Settings также действует на этот маршрут.

Журнал запросов сохраняет начало/ответ и итог операции с ID, портом, PID, build ID, MVID и поколением документа.
Полные аргументы и снимок модели в журнал по умолчанию не попадают. Подробная диагностика доступна в ограниченном хранилище результатов.

## Горячая перезагрузка MEP

`IReloadableAddinProvider.Reload()` реализует стабильный загрузчик, не выгружаемый расчётный модуль.
Он возвращает новый поставщик, проверяет фактическую загрузку и выбрасывает исключение при ошибке.
Реестр хранит стабильный загрузчик отдельно от текущего обработчика команд.
Возвращённый обработчик не обязан реализовывать IReloadableAddinProvider.
Повторные Reload и TryEnter/lease для всех поколений используют исходный стабильный загрузчик.
Он не должен сохранять ссылки на устаревший модуль после его замены.
При снятии регистрации или ошибке перезагрузки Cortex освобождает ссылки на обработчик и загрузчик.
Перезагрузка занимает тот же слот и общую блокировку плагина. Открытая транзакция запрещает вход.
Без заявленной поддержки Cortex возвращает `ReloadUnsupported`; универсального обхода загрузчика нет.
Новый MVID должен отличаться от старого. Повторная загрузка того же MVID не объявляется обновлением.
После успеха обновляются схемы, версия и поколение. Старые результаты сохраняют исходную версию.
При ошибке поставщик становится `unavailable`: прежний модуль мог уже выгрузиться.

В MEP `HotLoader.LoadOrReload` сейчас только записывает некоторые ошибки в журнал.
Адаптер должен превращать такую ошибку в проверяемый отказ, а не считать отсутствие исключения успехом.
`InvokeRequest`/очередь окна не подходят для синхронного вызова из Cortex.
MEP должен выделить общие команды для окна и адаптера; расчётные формулы остаются в MEP.
Предварительный набор из Issue #3: state.read, heating.capture/validate/calculate,
ufh.capture/set_inputs/calculate/save_results, ufh.boundaries.preview/apply, report.export.

Коллективно выгружаемый AssemblyLoadContext должен использовать **тот же** экземпляр сборки RevitCortex.Core,
который содержит реестр Cortex. Не загружайте приватную копию Core внутрь контекста MEP.
Загрузчик должен снять старые события, окна и обработчики, завершить транзакции и освободить старые ссылки.
Cortex освобождает свой дескриптор выполнения и обработчики отмены после завершения.
Одна копия реестра обслуживает один процесс; отдельные процессы Revit имеют независимые реестры.

## Демонстрационный поставщик и установка

Исходники: `examples/RevitCortex.SampleProvider`. Он не входит в штатную установку Cortex.
`test.element_count` читает количество нетиповых элементов.
`test.set_project_number` меняет Project Number только при точном совпадении указанного заголовка с активным проектом.
Дополнительно заголовок должен начинаться с `CORTEX_TEST_`. Семейства и рабочие проекты запрещены.
`injectWarning=true` создаёт контролируемое предупреждение Revit для проверки обработки сбоев.
Не используйте демонстрацию для изменения рабочих моделей.

```powershell
dotnet build examples/RevitCortex.SampleProvider/RevitCortex.SampleProvider.csproj -c Release
```

Первичная установка требует закрыть **все** Revit после сохранения проектов.
Сделайте резервную копию прежних Plugin/Tools/Core и MCP Server. Обновляйте комплект согласованно.
Установите Cortex обычным скриптом репозитория. Перезапустите MCP-клиент после замены сервера.
Демонстрационную DLL поместите рядом с Cortex, без второй копии Core.
Создайте отдельный пользовательский `.addin` по шаблону ниже и укажите абсолютный путь DLL.
Это отдельный явный шаг, который штатный установщик не выполняет.

```xml
<RevitAddIns>
  <AddIn Type="Application">
    <Name>Cortex Sample Provider</Name>
    <Assembly>C:\ABSOLUTE\CORTEX\RevitCortex.SampleProvider.dll</Assembly>
```

## Проверки и границы готовности

Модульные тесты проверяют контракт без запущенного Revit. Они не доказывают поведение нативных транзакций.
Демонстрация компилируется, но в рабочую модель не устанавливалась и не запускалась.

| Пункт | Автоматическая проверка | Проверка после установки в Revit |
|---|---|---|
| T01 | Реестр, схемы, версии, несовместимый API | `addin_list` показывает установленный cortex-test |
| T02 | Приём, единственный слот, вызов fake-provider | test.element_count без окна/выделения/смены вида |
| T03 | Неизвестная команда, неверные аргументы/режим/поколение | Повторить ошибочные запросы; модель не меняется |
| T04 | Смена токена/поколения до события и во время подтверждения | Принять запрос, переключить документ до обработки события; новый документ не изменён |
| T05 | Раздельное фиксированное TCP-соединение | Два Revit: instanceId/PID/порты различаются, команда идёт только в выбранный |
| T06 | Один UUID выполняется один раз, конфликт отклоняется | Повторить commit с тем же UUID; одна фактическая запись |
| T07 | Повтор без повторного вызова и доступ к статусу при занятом UI | Оборвать клиентский ответ; запросить статус по исходному UUID |
| T08 | Отмена/истечение до запуска, поздний вызов запрещён | Задержать обработку события, отменить; параметр не меняется |
| T09 | Исключение, неверный результат, ошибка очистки | Ошибка тестового заголовка возвращается с объяснением |
| T10 | Проверка обязательного подтверждения отката | probeRollback меняет значение внутри группы, возвращает исходное значение и rolledBack |
| T11 | Контракт не принимает ложный успешный итог | commit и probeRollback с injectWarning=true: failed, rolledBack, исходное значение, список сбоев, без EffectsMismatch и ручного окна |
| T12 | Новый MVID/поколение, отказ старого контекста, ошибка загрузки | С будущим адаптером MEP: два последовательных обновления DLL; новый MVID, сохранённый загрузчик, отсутствие старых обработчиков |
| T13 | Read-only до приёма/перед выполнением/в разных режимах | Settings Read-only блокирует запись, чтение работает |
| T14 | Выгрузка, занятость, устаревший дескриптор регистрации | Снять регистрацию через загрузчик; unavailable, старый обработчик не вызывается |

Повторите T10/T11 только в отдельном проекте `CORTEX_TEST_Addins` с заранее записанным Project Number.
Проверьте значения до/после отдельным чтением, а не только признак в ответе команды.
Не запускайте повтор неизменённого запроса после нативного сбоя или неизвестного итога.

После адаптации MEP выполните совместный сценарий: считать сеть → проверить → рассчитать → получить отчёт.
Затем отдельно проверьте запись результатов в Floor и последующее чтение.
Ни эти сценарии, ни обновление MEP не заявлены завершёнными текущей реализацией Cortex.
