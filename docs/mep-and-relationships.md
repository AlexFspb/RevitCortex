# Трубы, воздуховоды и связи элементов

Дата: 3 ноября 2026 года. Revit 2026 / .NET 8.
Локальная сборка: `2026.11.03-mep-relationships.16`.

## Назначение и источники

Добавлены три команды:

- `create_pipe` создаёт один прямой участок настоящей трубы Revit.
- `create_duct` создаёт один прямой участок жёсткого воздуховода Revit.
- `get_element_relationships` читает связи элементов и вложенных семейств.

Создание использует шаблон вызовов `Pipe.Create` и `Duct.Create` из [Demolinator/revit-mcp-server](https://github.com/Demolinator/revit-mcp-server/blob/0b8d5cebf0d23a21a2ffccee9e85bba614d71c7c/revit_mcp/mep.py).
Чтение связей основано на [oakplank/RevitMCP](https://github.com/oakplank/RevitMCP/blob/b00c193922212c34b50b2100a3461e526917a4a8/lib/routes/element_routes.py).
Оба источника используют MIT. Уведомления исходного проекта в `LICENSE` сохраняются.
Реализация перенесена на C#. Python и pyRevit для этих команд не требуются.

## Контекст и единицы

Сначала проверьте порт и документ через `get_project_info`.
Все ID относятся к активному документу этого подключения.
MCP-сервер сохраняет существующую привязку к порту и поколению документа.
При изменении контекста команда требует повторной проверки документа.

Координаты `startPoint` и `endPoint` имеют вид `[x,y,z]` и задаются в миллиметрах.
Начало координат — внутреннее начало модели Revit. Это не общие геодезические координаты.
Диаметр, ширина и высота также задаются в миллиметрах.
В отличие от `author_structural_members`, эти команды не принимают координаты в футах.

## Создание трубы

Аргументы `create_pipe`:

| Аргумент | Назначение |
|---|---|
| `systemTypeId` | ID `PipingSystemType` |
| `pipeTypeId` | ID `PipeType` |
| `levelId` | ID опорного уровня |
| `startPoint`, `endPoint` | По три координаты в мм |
| `diameterMm` | Положительный диаметр |
| `dryRun` | По умолчанию `true` |

Используйте ID из проверенной модели. Тип трубы и тип системы должны существовать в проекте.
Команда не выбирает первый доступный тип при ошибочном ID.
Получайте ID типов из данных модели, например через `ai_element_filter` с `includeTypes=true`, или из параметров существующего участка.
Тип системы нельзя подменять ID экземпляра системы.

## Создание воздуховода

Аргументы `create_duct`: `systemTypeId`, `ductTypeId`, `levelId`, `startPoint`, `endPoint`, `shape` и `dryRun=true`.
`systemTypeId` должен указывать на `MechanicalSystemType`, а `ductTypeId` — на `DuctType`.
Форма выбранного типа должна совпадать с `shape`.

| `shape` | Обязательные размеры | Недопустимые размеры |
|---|---|---|
| `round` | `diameterMm` | `widthMm`, `heightMm` |
| `rectangular` | `widthMm`, `heightMm` | `diameterMm` |
| `oval` | `widthMm`, `heightMm` | `diameterMm` |

Команда создаёт один прямой участок. Она не строит трассу из нескольких участков.
Команда не запрашивает создание фитингов, соединение существующих коннекторов, изменение уклонов, сохранение или синхронизацию.
Состояние соединений нужно проверять отдельно.

## Проверка и откат создания

Сначала выполните `dryRun=true`. При предварительной проверке изменения отсутствуют.
Проверяются входные данные, ID, форма типа, границы координат и длина участка.
Минимальная длина составляет 2,54 мм. Дополнительно действует `Application.ShortCurveTolerance`.
Весь запрос создания ограничен 16 Ки символов. Неконечные числа и неизвестные поля отклоняются.
Предварительная проверка не подтверждает допустимость выбранного размера и размещения внутри Revit.
Эти условия проверяются при создании.

Для применения передайте `dryRun=false`.
При выключенном автовыполнении Cortex запросит обычное разовое подтверждение.
После подтверждения команда снова проверит документ и изменение модели.
Режим «только чтение», отключение отдельных инструментов и аудит сохраняются.

Транзакция получает `ScriptFailureHandling.Configure(tx, rollbackOnWarnings: true)` после `Start()` и до изменений.
Это подключает `IFailuresPreprocessor` и `SetClearAfterRollback(true)`.
Предупреждение, ошибка или несовпадение результата отменяет создание.
Группа транзакций остаётся открытой до проверки результата после фиксации транзакции.
Проверяются фактические тип, тип системы, опорный уровень, концы оси и размеры.
Для отдельного участка объект `MEPSystem` может отсутствовать. Тип системы проверяется через встроенный параметр.

Ответ об ошибке содержит примитивные описания сбоев, важность, ID затронутых элементов и состояние отката.
После подтверждённого отката ответ не представляет отменённый участок как созданный.
Неизвестный результат требует проверки модели. Сетевой таймаут не останавливает нативный код Revit.
Не повторяйте создание автоматически после неопределённого результата.

## Чтение связей элементов

Аргументы `get_element_relationships`:

| Аргумент | Значение по умолчанию и ограничение |
|---|---|
| `elementIds` | Обязательный список, от 1 до 100 положительных ID |
| `includeHostChain` | `true` |
| `maxDepth` | `8`, допустимо 1–16 |
| `includeSubComponents` | `true` |
| `includeInserts` | `true` |
| `includeDependents` | `false` |
| `includeAdaptivePoints` | `true` |
| `maxRelated` | `50`, допустимо 1–100 для каждого списка |

Повторяющиеся запрошенные ID объединяются. Сохраняется порядок первого появления.
Для каждого уникального ID возвращается результат или явная причина отсутствия данных.
После исчерпания бюджета ответа оставшиеся ID получают состояние `not_read`.
Они не исчезают из ответа без объяснения.

Команда различает:

- основу размещения `host` и родительский экземпляр `superComponent`;
- группу и сборку;
- ограниченную цепочку основ и родительских компонентов;
- вложенные компоненты;
- вставки в поддерживаемой основе;
- зависимые элементы через `GetDependentElements`;
- точки размещения адаптивного компонента.

Для связей различаются успешное чтение, отсутствие, неприменимость, отключение и ошибка.
Списки сообщают количество возвращённых данных и признак усечения.
Координаты адаптивных точек возвращаются в мм относительно внутреннего начала модели.
Ошибка чтения одного поля не подменяется пустым результатом.

ID внутри связанного документа не разрешаются через основной документ.
Связь с документом RevitLinkInstance обозначается как граница обхода.
Цепочка ограничена глубиной и обнаруживает циклы.
`FindInserts` может включать проёмы и встроенные стены, а не только двери и окна.
`GetDependentElements` возвращает определённые Revit зависимости. Он не перечисляет все смысловые связи модели.
Граница ответа ограничивает возвращаемые данные. Сами нативные методы Revit могут сначала собрать более длинный список ID.

## Ручная проверка в Revit

Используйте отдельный тестовый проект.

1. Проверьте предварительное создание трубы, круглого и прямоугольного воздуховода. Изменений быть не должно.
2. Создайте по одному участку. Проверьте ось, размеры, тип, тип системы и опорный уровень.
3. Отмените каждый результат одним шагом. Участок должен исчезнуть.
4. Проверьте отказ при неверном ID, несовпадающей форме, недопустимом размере и слишком коротком участке.
5. Вызовите предупреждение Revit. Проверьте полный откат и диагностический ответ.
6. Проверьте ручной отказ, режим «только чтение» и смену документа между предварительной проверкой и записью.
7. Прочитайте связи двери со стеной, вложенного семейства, группы, сборки и адаптивного компонента.
8. Проверьте ограничения списков и отсутствие ID. Ошибка должна отличаться от отсутствия связей.
9. Прочитайте экземпляр с основой в связанном файле. ID связанного элемента не должен разрешаться через основной документ.
10. Повторите проверку на втором порту. Команды не должны переходить в другой Revit.

Обычные тесты и проверка каталога MCP не заменяют эти нативные проверки.
