## Проблема

MCP-инструкции прямо запрещали `Document.EditFamily` из `ExternalEvent` и объясняли запрет неизбежным зависанием.
Описание смешивало программное получение документа семейства и интерактивное открытие редактора.
Оно также смешивало внешнее событие и динамическое обновление.

Документация Autodesk запрещает вызов при определённых состояниях документа и семейства, но не устанавливает общий запрет для `ExternalEvent`.
Кроме того, существующие `ExportFamiliesTool` и `ListFamilySizesTool` уже вызывают `EditFamily` через стандартный путь выполнения Cortex.
Наличие этих вызовов само по себе не доказывает безошибочность всех семейных операций.

## Новый порядок применения

- `EditFamily` допустим в корректном контексте API. Он сам по себе не является модальным окном.
- Для семейных C#-процессов инструкция требует `transactionMode=none`.
- Проверяются исходный документ, принадлежность семейства, `IsEditable` и `IsInPlace`.
- Изменения семейства требуют отдельных транзакций, обработки сбоев и проверки статуса.
- Загрузка обратно требует явного `IFamilyLoadOptions`. `RevitUIFamilyLoadOptions` исключён из автономного процесса.
- Созданный фоновый документ закрывается в `finally`. Ошибка закрытия не должна скрывать исходную ошибку.
- Данные нужно материализовать до закрытия документа.
- Сохранение, загрузка обратно и фиксация отдельных транзакций не образуют одной атомарной операции Cortex.
- Таймаут не прерывает уже выполняющийся вызов API. Слепой повтор запрещён.

Выбор `none` вместо `group` — правило этого процесса Cortex.
Документ не утверждает, что открытая группа всегда запрещает сам `EditFamily`.

## Согласованное поведение

Порты Release остаются 8080/8888 с автоматическим выбором. Dev остаётся 8081/8889.
Обычные операции сохраняют включённый по умолчанию автоматический запуск через три секунды.
C# сохраняет отдельное подтверждение и необязательный автоматический запуск через три секунды в текущем сеансе.
Окна OK при запуске и остановке сервера не добавлены.
Правило отдельного согласования C# в чате не возвращено.
Проверка кода, аудит, разрешения и режим «только чтение» сохраняются.

Обратите внимание на два разных правила предупреждений:

- Стандартный `ScriptFailureHandling.Configure(tx)` записывает предупреждения и удаляет их из окна, но откатывает ошибки.
- Текущая пользовательская инструкция для собственных скриптов требует отката при неожиданных предупреждениях тоже.

Эта модификация не меняет стандартный обработчик. Документация прямо требует более строгий обработчик, когда этого требует задача.
Не считайте вызов стандартного `Configure(tx)` достаточным для выполнения более строгой пользовательской политики.

## Что особенно проверить по коду

1. Удалён ли общий запрет из всех действующих каналов, которые читает агент?
2. Не обещает ли новая инструкция безопасность или автоматический откат, которых исполнитель не обеспечивает?
3. Верно ли разграничены `ExternalEvent`, `IUpdater`, транзакция и группа транзакций?
4. Указана ли нужная перегрузка загрузки: `familyDocument.LoadFamily(targetDocument, IFamilyLoadOptions)`?
5. Не потеряны ли ограничения подтверждений и режима «только чтение»?
6. Достаточно ли ясно указано, что поля `stage`, `reloaded` и `cleanupError` формирует скрипт, а не Cortex?
7. Не скрывает ли документация ограничения пробного прохода без фиксации?
8. Понятно ли, что клиент получает новую инструкцию после обновления MCP-сервера и переподключения?
9. Доступен ли полный документ в автономно установленном навыке без ссылки за пределы его папки?
10. Нужен ли следующим отдельным изменением готовый тип `IFamilyLoadOptions` или специализированный инструмент?

Последний пункт — оценка следующего этапа. В этом изменении такие типы и инструменты не реализованы.
Произвольный скрипт не получает автоматическую безопасную загрузку семейства только от изменения описания.

## Проверки в Revit, которые ещё не выполнены

Проводите проверки на копии проекта с одним небольшим семейством.
Сначала уточните порт и проверьте активный документ.

| Сценарий | Что подтвердить |
|---|---|
| `none`: открыть, прочитать, закрыть семейство | Примитивный ответ; фоновый документ закрыт; проект остаётся активным |
| `auto`: вызвать `EditFamily` | Понятная ошибка API; подтверждённый откат; нет утверждения о неизбежном зависании |
| Неизменяемое семейство или неверный документ | Отказ до изменений с понятной причиной |
| Ошибка после открытия семейства | Очистка выполняется; исходная ошибка сохраняется |
| Пробное изменение и откат | Нет SaveAs/LoadFamily; исходный проект не изменён |
| Ошибка или предупреждение в собственной транзакции | Соблюдена политика задачи; возвращены описание, severity и ID |
| Загрузка обратно с конфликтом | Явные решения IFamilyLoadOptions; нет интерактивного запроса |
| Ошибка после сохранения или загрузки | Ответ не обещает откат выполненных внешних действий |
| Ленивый результат из семейства | Материализован до закрытия; нет обращения к закрытому документу |
| Два экземпляра Revit | Закрытие фонового семейства не останавливает сервер и не меняет целевой проект |

Не воспроизводите нативные падения на рабочей модели.
Не проверяйте таймаут искусственным бесконечным циклом в потоке Revit.
В этой сессии работающие экземпляры Revit, установленные DLL и локальные навыки не изменялись.
